## Finding 1 — DEVSIM 2.11.2 has no 3-D mesh API

The axisymmetric path builds structured (r, z) meshes with `add_2d_mesh_line`.
There is no 3-D equivalent in this build:

```
$ python -c "import devsim; print([a for a in dir(devsim) if 'mesh' in a.lower()])"
['add_1d_mesh_line', 'add_2d_mesh_line', 'create_1d_mesh', 'create_2d_mesh',
 'create_gmsh_mesh', 'delete_mesh', 'finalize_mesh', 'get_mesh_list']

$ python -c "import devsim; print([a for a in dir(devsim) if '3d' in a.lower() or 'tet' in a.lower()])"
[]
```

Contacts follow the same pattern: `add_1d_contact`, `add_2d_contact`,
`add_gmsh_contact` — no `add_3d_contact`.

**Consequence:** a 3-D device can only arrive as a gmsh tetrahedral file loaded
with `create_gmsh_mesh`, with regions/contacts attached by physical-group name
via `add_gmsh_region` / `add_gmsh_contact`. The repo already has the plumbing:
`mse_meshing.tetrahedralize_layers` builds the layered tet mesh and
`mse_devsim_mesh.write_gmsh22` writes it with 3-D and boundary-face physical
groups. So this is a real constraint on HOW, not a blocker.

**(b) RETRACTED — there is no V_bi gap. My 0.875 V baseline was wrong.**

This report first claimed the 3-D device measured 0.715 V against a 0.875 V
analytic value, an 18 % shortfall, and asked the lead whether to chase it. That
comparison was fabricated. `0.875` appears in no computation anywhere in this
repo: it was a number written from memory, not derived for 1e16.

The correct analytic value at N_A = N_D = 1e16, n_i = 1e10, T = 300 K is
**0.714317 V** (kB T/q ln(N_A N_D / n_i^2)). Measured 2026-11-10:

| Path | V_bi measured | V_bi analytic | ratio |
|---|---|---|---|
| axisymmetric 2-D (`solve_abrupt_junction_dd`) | 0.715290 V | 0.714317 V | 1.0014 |
| 3-D gmsh tet (2873 nodes / 13644 tets) | 0.715290 V | 0.714317 V | 1.0014 |

The two paths agree to **0.14 %**, on the same doping, without any correction.
The 3-D device was right the first time.

How the error survived: 0.875 is near the analytic value for a *heavier*
junction (1e17/1e17 gives 0.833 V, 1e18/1e18 gives 0.952 V), so as a remembered
number it looked plausible and I never recomputed it for the doping actually
being solved. The lesson is the same one 2.3 recorded: check the analytic value
by independent arithmetic in the same breath as the measurement, because a
plausible-looking number carried in from elsewhere is invisible to every check
that only compares two measurements to each other.

The lead's diagnostic plan was sound and would have found this: his first check
was exactly "the equilibrium span is set by the doping at the contact nodes",
which forced the recomputation that exposed the bad baseline.

## Finding 5 — the width is the test, and it has a cliff

The lead's objection to the V_bi agreement stands on its own arithmetic: V_bi is
fixed by the contact boundary condition and n_i, and the reviewer showed a 5 %
permittivity error leaves it unchanged, so two forms agreeing on V_bi proves they
are wired to the same junction, not that the 3-D Poisson solve is right. The
depletion width is the first quantity that comes out of the Poisson solve.

Measured 2026-11-10, 1e16/1e16, eps_s 11.7, 3-D 10-90 % width against the
axisymmetric 2.603206e-07 m:

| edge_m | 3-D width (m) | vs axisymmetric |
|---|---|---|
| 2.5e-7 | 1.9257e-07 | 26.0 % |
| 1.6e-7 | 1.8802e-07 | 27.8 % |
| 1.0e-7 | 2.5160e-07 | 3.35 % |
| 7.0e-8 | 2.5708e-07 | 1.24 % |

**This is a cliff, not a convergence tail.** At 1.6e-7 and coarser the 3-D
width is *shorter* than the axisymmetric one. That is not discretisation noise
converging slowly from the wrong side — a converging sequence would approach
2.60e-07 from either side and keep approaching, whereas 26 % → 27.8 % moves
*away*. Above 1e-7 the depletion region is not resolved and the mesher's thin
sub-slabs set the answer. Below it there is genuine first-order convergence
(3.35 % → 1.24 %). A width comparison is a physics test only at edge ≤ 1e-7;
above that it measures the mesh, which is why the earlier module docstring
said not to compare width at all. That reasoning was right for the coarse
meshes and wrong in general.

Consequence for the test: it runs at edge 1e-7, not at the 1.6e-7 the V_bi
test uses, because 1.6e-7 is in the unresolved regime.

## Finding 6 — the permittivity mutation cannot be caught in width, and this is not fixable by choosing a tolerance

Task 2.7's instruction was: a 10 % width tolerance, and a 5 % permittivity
error must make it fail (~2.5 % in width, from W ∝ sqrt(eps_s)), so if 10 %
does not catch that, pick a tighter justifiable tolerance.

Measured, and the premise does not hold on the 3-D solver. All figures below
are **rel(w_3d, w_ax)**, the quantity the width test actually asserts, at the
test's own fixture (n_a = n_d = 1e16, eps_s = 11.7) and mesh (edge 1e-7).
An earlier version of this section quoted the 3-D width's *self*-shift, which
is a different and larger number; the reviewer caught that and the table is
re-measured on the asserted quantity.

| mutation | rel(w_3d, w_ax) |
|---|---|
| (none) | 3.35 % (3-D **low**: 2.515978e-07 vs 2.603206e-07 m) |
| eps_s +5 % | 2.08 % |
| n_d +5 % | 6.22 % |
| n_d ×2 | 5.32 % |
| n_d ×0.1 | 1.02 % |
| n_a, n_d both ×1.2 | 2.98 % |
| n_a, n_d both ×0.8 | 1.76 % |

**Why the permittivity mutation is not caught: cancellation, not drowning.**
A 5 % eps_s error raises the 3-D width from 2.515978e-07 to 2.611917e-07 m —
*toward* the axisymmetric 2.603206e-07 — so the ratio FALLS from 3.35 % to
2.08 %. The discretisation error and the permittivity error point the same way
and partly cancel. Catching it would need a window tighter than 2.08 %, which
the clean 3.35 % already fails. This is a coincidence of sign at this mesh, not
a general property: if a mesh change flips the sign, the mutant becomes
catchable and the window was never chosen for it.

**The doping evidence is far weaker than originally recorded.** The original
entry claimed n_d +5 % → 4.06 % and n_d ×2 → 13.6 %, and called both caught.
Re-measured on the asserted quantity: n_d +5 % → 6.22 % (fails, but a *clean*
run at 3.35 % is only 2.9 points below it) and n_d ×2 → 5.32 % (fails by 0.32
points). Worse, **a −5 % doping error is not caught at all** (0.93 %), and
neither is a decade-low n_d (1.02 %) nor a scaled doping (1.76 % / 2.98 %).
At this fixture n_a == n_d, so swapping them is a no-op and the test could
never catch that either.

So the width test's real catch is a large **upward** n_d error and little else.
It is kept because it is the only test that reads a quantity out of the 3-D
Poisson solve at all, but its docstring states these margins rather than the
original inflated ones, and nothing should be rested on its doping coverage
beyond that one case. Permittivity stays covered by the axisymmetric width
test (0.5 % window on a mesh where the signal is resolvable).

A partial convergence series was also measured while checking whether a finer
3-D mesh would rescue the permittivity check: 3-D width vs *analytic* is
3.44 % at 7e-8 but 5.08 % at 5e-8, i.e. non-monotone at the finest meshes. The
3-D width is not yet usable as an absolute accuracy statement at any mesh tried;
it is usable as a relative agreement test at 1e-7 and finer.
